# Hosted Mode RFC

## Status

Proposed

## Problem

Aimux has exactly two deployment shapes today, and neither fits a shared box.

**Local mode** (`aimux ui`, `connectionMode: "local"`) serves the first-party web bundle from
`dist-ui` and lets the browser call the daemon on `43190` and each project service on its own port
directly. There is no authentication anywhere in that path: `metadata-server` binds `127.0.0.1` and
treats loopback as the trust boundary, `send()` defaults `access-control-allow-origin: *`, and
`isAllowedCorsOrigin` accepts any `http://localhost|127.0.0.1` origin. That is correct for one
person on their own machine and unusable for anything else.

**Relay mode** authenticates properly — Clerk on the client socket, an HS256 daemon token on the
daemon socket, one Durable Object per owner — but the model is single-owner by construction. The
only other principal that exists is a read-only share guest. `assertRemoteAccessAllowed` knows two
roles: `owner`, which can reach every route including spawn/kill/worktrees, and `guest`, which is
`GET`-only on four session-read routes. There is nothing in between.

The missing shape is a **service host**: one machine, several principals, each pinned to their own
session, each able to converse with it and do nothing else — with connection activity reported
somewhere a human will actually see it.

## Non-goals

- Replacing the relay. Relay mode stays exactly as it is; hosted mode is a third door, not a
  migration.
- Changing any loopback behaviour. Everything in this RFC is additive and default-off.
- Terminating TLS, or being an internet-facing server. Hosted mode expects a tunnel or reverse proxy
  in front of it.
- Owning notification delivery. Hosted mode emits signed events; where they go is the deployer's
  business.

## What hosted mode is not solving

Worth stating plainly, because it shapes how much the role model is worth: an operator who can send
text to a session is talking to a tool launched as
`codex --dangerously-bypass-approvals-and-sandbox`. Restricting the API surface does not restrict
the agent. The route allowlist stops an operator from spawning agents, reading other people's
sessions, and driving the daemon; it does not and cannot stop them from asking their own agent to
do something. The boundary that carries real weight is the one outside aimux — the OS user, the
credentials on the box, what the box can reach.

Hosted mode's value is multi-tenancy plumbing: principals, pinned sessions, tokens, audit, events.
It should be built and reviewed as plumbing, not sold as a sandbox.

## Design

### The listener is separate, and off by default

Do not rebind the daemon. Add an opt-in HTTP listener (`src/hosted-server.ts`) that authenticates
every request, resolves a principal, checks the allowlist, and then hands the request to the
existing `daemon.routeRequest(method, path, body, headers)` — the same entry point the relay client
uses. No route logic is duplicated, and an installation that never enables hosted mode is
byte-for-byte unaffected.

Default bind stays `127.0.0.1`, on its own port (`43195`). A tunnel daemon (`cloudflared` and
friends) runs on the box and dials loopback, so hosted mode gets remote reach without ever listening
on a public interface. `bindAddress` is configurable for LAN deployments, but binding off-loopback
with no principals configured is refused at startup rather than warned about.

### Identity comes from a token, never from a header

`parseRemoteActor` trusts `x-aimux-*` headers because today only the relay's Durable Object can set
them. The moment a request can arrive from a tunnel, those headers are attacker-controlled.

So the hosted listener **strips every `x-aimux-*` header off the inbound request before anything
else looks at it**, then derives the actor itself from a bearer token and injects its own trusted
headers downstream. That ordering is the single most important line of code in this RFC and belongs
in its own tested function.

Tokens are opaque, generated by the CLI, and stored only as a SHA-256 hash in
`~/.aimux/hosted/principals.json`:

```jsonc
{
  "principals": [
    {
      "id": "prn_a1b2c3",
      "label": "grand:admin:user_2abc",     // deployer's own identifier, opaque to aimux
      "tokenHash": "sha256:…",
      "role": "operator",
      "grants": [{ "projectRoot": "/srv/grand", "sessionId": "assistant-sam" }],
      "createdAt": "…",
      "revokedAt": null
    }
  ]
}
```

### The operator role

Third value on `RemoteActorRole`. Rules, enforced in `assertRemoteAccessAllowed`:

- Only reachable through the `/proxy/<host>/<port>/<subpath>` form, as guests already are — daemon
  routes are refused outright.
- Allowed subpaths: `/agents/input`, `/agents/output`, `/agents/interrupt`. Everything else — spawn,
  fork, stop, kill, migrate, worktrees, services, graveyard, threads, tasks, shell state, plugin
  runtime — is denied by default. The allowlist is a map of route to permitted method, so a new
  route added elsewhere in the codebase is denied until someone deliberately adds it here.
- `/agents` (list) is **denied**: it returns every session in the project, which would leak other
  principals' session ids, tools and tasks. A filtered listing needs its own route.
- The proxied service port is resolved back to a project root, and a grant is checked against that
  root — not against the session id alone. Resolution requires a *live* service and refuses an
  ambiguous match, because endpoint records outlive their process and ephemeral ports get recycled.
- Every allowed request must carry a `sessionId`, and it must appear in the principal's grants.
  Missing session id is a 403, not a fallthrough. This mirrors the existing `shareSessionId` check
  and should share its test shape.
- `/agents/output/stream` and `/events` are **out of scope for v1** — SSE through the hosted
  listener needs its own streaming path (`routeRequest` returns JSON), and polling `/agents/output`
  is what the reference consumer does anyway. Denied like anything else until implemented.

### Rate limiting and caps

Per-principal token bucket on requests/minute, a prompt-size cap on `/agents/input`, a concurrency
cap, and a response-size cap. Defaults live in config; all four are the difference between a stuck
client and a runaway one.

### Audit

Append-only JSONL at `~/.aimux/hosted/audit.jsonl`, rotated by size. One record per request:
timestamp, principal id and label, method, path, session id, status, request and response byte
counts, and — for `/agents/input` — the prompt text plus its hash. Prompts are the interesting
artifact; a deployment that would rather not keep them can turn the body off and keep the hash.

### Connection events

Hosted mode emits security-relevant events and delivers them to a configured webhook. It does not
send email, push, or anything else — the deployer's system decides what a human sees. Events:

| kind | when |
|---|---|
| `hosted_token_first_use` | a principal's token authenticates for the first time |
| `hosted_new_device` | a known principal appears from an unseen device fingerprint |
| `hosted_auth_failed` | bad or revoked token (throttled, never echoes the token) |
| `hosted_token_revoked` / `hosted_grant_changed` | CLI mutations |
| `hosted_lockdown` | lockdown engaged or cleared |

Device fingerprint is `sha256(ipHashSecret + ip + userAgent)` — pseudonymised the way the relay
already handles IPs, so events are correlatable without storing addresses. Payload carries the
principal id and label, session id, fingerprint, user agent, and any `cf-ipcountry`.

Delivery is `POST {hosted.webhookUrl}` with `x-aimux-signature: sha256=<hmac>` over
`{timestamp}.{body}` and `x-aimux-timestamp` for replay rejection, secret read from the environment
variable named by `hosted.webhookSecretEnv`. Retry with backoff, bounded queue, drop with a log line
rather than blocking a request. Events also always land in the audit log, so a webhook outage loses
notification timeliness, not the record.

### Lockdown

`aimux hosted lockdown on` makes every hosted route 503 and emits an event. It does not touch tmux
or the loopback surface — an operator loses their door, the owner keeps theirs.

## Config

Hosted config lives in the **global** config (`~/.aimux/config.json`) only, and never joins
`AimuxConfig`. Project config is committed in repos, so letting `.aimux/config.json` reach these
fields would mean cloning a repo could enable a listener or move its bind address. `normalizeConfig`
strips any `hosted` key that arrives from the project layer.

```jsonc
"hosted": {
  "enabled": false,
  "bindAddress": "127.0.0.1",
  "port": 43195,
  "rateLimit": { "requestsPerMinute": 60, "maxConcurrent": 4 },
  "maxPromptBytes": 16384,
  "maxResponseBytes": 1048576,
  "auditPromptBodies": true,
  "webhookUrl": null,
  "webhookSecretEnv": "AIMUX_HOSTED_WEBHOOK_SECRET"
}
```

## CLI

```
aimux hosted status
aimux hosted token create --label <label>          # prints the token once, stores only the hash
aimux hosted token list | revoke <principalId>
aimux hosted grant <principalId> --project <root> --session <id>
aimux hosted ungrant <principalId> --session <id>
aimux hosted audit tail [-n]
aimux hosted lockdown on|off
```

## Files

| path | role |
|---|---|
| `src/hosted-config.ts` | `HostedConfig` type, defaults, global-only load, validation (refuse off-loopback bind with no active principals) |
| `src/hosted-principals.ts` | principal store, token hashing, grant lookup, lock-guarded mutation |
| `src/hosted-auth.ts` | header stripping, bearer verification, actor construction |
| `src/hosted-server.ts` | the listener; auth → limits → `routeRequest` → audit |
| `src/hosted-audit.ts` | JSONL writer + rotation |
| `src/hosted-events.ts` | event construction, fingerprinting, HMAC webhook delivery |
| `src/remote-access.ts` | `operator` role, allowlist, session pinning |
| `src/config.ts` | strip a project-supplied `hosted` key in `normalizeConfig` |
| `src/daemon.ts` | start/stop the listener when enabled |
| `src/main.ts` | `aimux hosted …` |
| `docs/hosted-mode.md` | operator-facing guide |
| `scripts/hosted-check.mjs` | end-to-end smoke, wired to a yarn script |

## Open questions

1. Does `operator` deserve a read-only sibling (`observer`) now, or later when something asks?
2. Should grants be by session id only, or should a principal be grantable a whole project?
3. Is the audit log a first-class stream (tail over the hosted API) or strictly a file?
