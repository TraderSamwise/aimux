Loop overseer UX v1

One project overseer session manages any number of assigned agents. Assignment is explicit project state, not a prompt convention. The overseer may change that state through aimux commands, and every client must render the resulting model.

Core rule: chat can request "watch this agent" or "stop watching this agent", but the source of truth is `session.loop.active`, `session.loop.goal`, and `project.overseerSessionId`. The UI should never infer loop membership from conversation text.

Implementation notes

State model

  • Session metadata owns `overseer`; the store enforces one active overseer per project.
  • Session metadata owns `loop.active`, `loop.goal`, and `loop.since` for watched agents.
  • Conversation requests are inputs, not state.

Overseer powers

  • Can call `aimux loop add/remove` for any project agent.
  • Can edit goals and mark done or blocked.
  • Must not nudge agents waiting on human input.

Client UX

  • TUI: badges plus a Loop Manager overlay.
  • GUI: project Loop screen plus agent manage sheet.
  • Mobile: same state, compact controls.
